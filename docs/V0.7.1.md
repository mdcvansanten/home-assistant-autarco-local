# Autarco Local v0.7.1 — Field-test UX, grouped polling and write readiness

v0.7.1 is the first follow-up to the v0.7.0 field test on the live Autarco installation.

## Changes from the field test

### Scenario-first now really means scenario-first

The existing scenario block is moved directly below the settings lock bar. Users see operating goals before individual registers/settings. The same scenario block is reused rather than duplicated, so the underlying v0.7.0 scenario definitions remain authoritative.

### Linked settings are visibly marked

Known cross-setting relationships receive a `🔗 Gekoppeld` badge in the rendered Settings UI. A configuration-health panel follows the scenarios and highlights proven blocking relationships such as `Reserve SOC >= Minimum SOC`.

### Installer/system settings start collapsed

Installer/system parameters remain available for diagnostics and later mapping, but no longer dominate the normal user flow.

### Current diagnostics versus historical errors

The Diagnose page now distinguishes:

- the current Modbus/TCP state;
- the latest active communication error, if any;
- the last historical disconnect reason;
- persistent connection history.

A recovered timeout therefore no longer looks like an active fault simply because it is the most recent historical disconnect reason.

## Grouped runtime polling

The original v0.6.x runtime reader scanned the full `33000-33170` range in <=10-register chunks. On the field installation complete polls were around 9.6–10.2 seconds.

v0.7.1 activates the device profile introduced in 0.7.0 and normally reads four validated logical groups:

1. clock/energy;
2. PV live;
3. inverter live;
4. battery/meter live.

If the inverter rejects one broad group, only that group automatically falls back to the proven small-chunk reader. Retry/reconnect behaviour remains unchanged.

Diagnostics expose the active strategy, request count and any fallback groups so the field test can compare latency and stability directly with v0.7.0.

## Deep connection monitoring

Field testing also showed recurring connection loss while the inverter/logger is connected over Wi-Fi. v0.7.1 therefore separates transport reachability from Modbus protocol health.

After **every failed runtime poll**, including failures that the normal coordinator deliberately suppresses to keep the previous valid values available, Autarco Local performs one independent TCP connection probe to port 502.

The monitor classifies the result as:

- `modbus_healthy` — the complete Modbus runtime poll succeeded;
- `tcp_502_down` — the Modbus poll failed and the independent TCP/502 probe also failed;
- `tcp_up_modbus_failed` — TCP/502 is still reachable but the Modbus runtime request failed.

The grouped poller additionally records the exact runtime group or fallback chunk being read when the failure occurred. Diagnostics expose the classification, failed group, TCP probe latency, request count, polling strategy and the last classified events.

A dedicated **TCP 502 bereikbaar** connectivity entity is exposed so Home Assistant Recorder can retain this layer separately from the normal Modbus connection state. The timestamps are intended to be correlated with the existing Ping integration and MikroTik Wi-Fi registration/log events. If Ping and TCP 502 disappear together, the problem is likely in the Wi-Fi/logger/network layer; if TCP remains reachable while Modbus fails, the logger/Modbus request path becomes the stronger suspect.

## Controlled write opening

v0.7.1 adds an explicit write-readiness registry. Solis compatibility is a reference, never proof that an Autarco write is safe.

Current qualification order:

1. **Minimum-SOC off-grid** — hardware validated;
2. **Reserve SOC** — next hardware candidate;
3. work-mode and Battery Reserve transitions — dependency validation;
4. Time-of-Use and schedule/current transactions — dependency validation;
5. Grid Charging / Force-charge settings — mapping and interaction validation;
6. installer/factory protection values — remain read-only unless there is a strong reason and authoritative validation.

Every newly opened setting must use fresh pre-read, complete affected-state snapshot, relation checks, write, read-back, conflict detection, restore where temporary state was changed, and final verification.

No additional physical write is enabled merely by installing v0.7.1. The next field write candidate is Reserve SOC.
